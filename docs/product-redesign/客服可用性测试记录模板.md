# 售后工作台客服可用性测试记录模板

> 用途：给业务负责人组织 5 名非研发人员做无指导测试。
>
> 本文件是**记录模板与判定口径**，当前不填入模拟结果。只有实际邀请客服/主管并完成观察后，才能填写“实测结果”。

## 一、测试目标

验证新用户是否能在不阅读技术文档的情况下完成一张普通售后工单的核心闭环：

1. 找到需要优先处理的工单；
2. 看懂订单事实和当前下一步；
3. 判断是否需要主管审批；
4. 使用或修改回复草稿；
5. 记录内部备注并 @ 主管；
6. 在发送前知道系统为什么阻止或允许操作。

不测试模型效果、接口性能、数据库术语或 Agent 轨迹。测试主持人只观察用户是否能完成任务，不在过程中讲解“正确点击路径”。

## 三、主持人口令

主持人只读下面的任务卡，不提示按钮位置、状态名称或技术原因。用户卡片中的“客户”均为演示角色。

### 任务 A：找到下一步

“你刚登录售后工作台。请找到一张你认为应该优先处理的工单，并告诉我：客户遇到什么问题、现在下一步要做什么、是否已经超时。”

完成标准：用户能打开工单详情，并用自己的话说出问题、下一步和时限。不要要求用户说出 `SLA`、`risk_tier`、`agent` 等技术词。

### 任务 B：判断是否需要主管

“这张工单涉及退款或赔付。请判断你现在能不能直接发给客户，下一步应该怎么做。”

完成标准：用户能找到“需要人工决定/需主管审批”等业务提示，并知道未审批不能向客户承诺退款已执行。

### 任务 C：准备客户回复

“请使用一个常用回复作为起点，修改成你愿意发给客户的话，但先不要发送。”

完成标准：用户能套用模板、编辑草稿，能发现订单号/问题类型等变量缺失时需要补充；不得要求用户理解模板实现方式。

### 任务 D：内部协作

“请在不让客户看到的情况下，留一句备注并 @ 售后主管，请他关注这张工单。”

完成标准：用户进入内部协作区，提交备注，确认备注客户不可见；主管账号能在“待我关注”里找到该消息并标记已读。

### 任务 E：主管维护话术（主管组）

“请新增一条适用于物流问题的常用回复，并把它停用。”

完成标准：主管能打开“管理回复模板”，完成新增和停用；客服账号不应看到维护入口。模板操作不应直接发送客户消息。

## 五、量化判定

每项任务 1 分，独立完成得 1 分，否则 0 分。每位客服至少完成 A-D，主管至少完成 A、B、E。

| 指标 | 目标 | 实测结果 |
|---|---:|---:|
| 客服 A-D 独立完成率 | ≥ 80% | |
| 能正确识别需审批工单 | ≥ 4/5 人 | |
| 能找到并使用常用回复 | ≥ 4/5 人 | |
| 能完成客户不可见的内部备注 | ≥ 4/5 人 | |
| 主管完成模板维护 | ≥ 2/2 人 | |
| 因技术术语导致的卡顿 | 0 次为目标 | |
| 用户主动提出“下一步做什么”以外的技术问题 | 记录并改文案 | |

判定建议：

- 达标：客服 A-D 独立完成率达到 80%，且审批门禁、客户可见性没有发生高风险误解；
- 有条件达标：任务完成率达标，但有 1-2 个重复理解问题，进入下一轮文案/布局优化；
- 不达标：有人把“待审批”理解为“退款已经执行”，或把内部备注发给客户，必须先修复再扩大试用。

## 六、问题分级与改进闭环

| 级别 | 例子 | 处理要求 |
|---|---|---|
| P0 | 用户误发未审批退款承诺、内部备注对客户可见 | 立即阻断发布，先修复权限/门禁/文案 |
| P1 | 多人找不到下一步、看不懂审批状态、模板变量误导 | 下一轮迭代前修复并回测 |
| P2 | 用词不顺、按钮位置不明显、重复点击 | 纳入体验优化 backlog |

每个问题必须记录：复现步骤、参与者原话、影响岗位、建议改动、修复版本、回测参与者。没有实际参与者和观察记录时，不得填写“已解决”。

## 八、结构化记录（可选）

如需交给记录工具或验收脚本处理，可在 Windows CMD 生成 JSON 空白模板：

```cmd
\.venv\Scripts\python.exe backend\scripts\validate_usability_test_record.py --template-out docs\product-redesign\客服可用性测试记录.json
```

填写真实观察记录后，只输出不含用户原话的汇总：

```cmd
\.venv\Scripts\python.exe backend\scripts\validate_usability_test_record.py --input docs\product-redesign\客服可用性测试记录.json --summary-out docs\testing\artifacts\usability-test-summary.json
```

汇总只报告已填写任务数、独立完成率和 P0/P1/P2 问题数量，**不会替业务方判断产品是否达标**。预发布门禁只有在以下事实同时具备时，才会把“真实客服测试”单项标记为 `verified_external`：

- `participant_scope_confirmed=true`，且至少 5 名参与者逐人填写 `is_developer=false`；
- 18 项任务的 `completed`、`independent`、`duration_seconds` 均有真实观察值；
- `test_date`、`facilitator` 和正式 `conclusion` 已填写；
- 没有未解决的 P0/P1；出现过 P0/P1 时必须附 `remediation_retest` 或 `retest` 记录。

脚本会拒绝密码、电话、地址和 token 等敏感字段；参与者原话应保留在业务方受控记录中，不要写入汇总文件。空模板、自动化回归或开发人员自测都不会解除真实客服门禁。
