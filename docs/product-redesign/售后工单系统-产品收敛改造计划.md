# 电商售后工单系统产品收敛改造计划

> 版本：v1.0  
> 日期：2026-09-26  
> 当前定位：从“研发验证平台”收敛为“一线售后客服决策工作台”  
> 依据：现有运行系统、项目需求书、当前前后端实现与本地演示数据

## 1. 改造结论

当前系统的底层能力不需要推倒重做。订单事实、政策版本、风险门禁、审批、审计和状态机都有保留价值。真正需要重做的是产品入口、角色分层、信息层级和业务表达。

改造后的产品只回答一个问题：

> 客服打开一张工单后，能否在最短时间内知道客户遇到了什么、事实是否齐全、应该怎么处理、能否直接回复，以及下一步应该点击什么？

任何不能帮助用户回答以上问题的信息，都不进入客服主界面。

## 2. 产品目标与非目标

### 2.1 目标用户

| 角色 | 每天要完成的工作 | 系统必须提供的价值 |
|---|---|---|
| 一线客服 | 读取诉求、核实订单、给出回复、转派或补充信息 | 少查系统、少复制粘贴、减少错误承诺 |
| 售后主管 | 审核退款/赔付/争议工单 | 快速看清金额、事实、政策和风险 |
| 质检人员 | 抽查已处理工单 | 发现政策使用错误、回复不当和流程遗漏 |
| 系统管理员 | 维护接口、政策、角色和审计 | 保证系统可用、规则有效、权限正确 |

### 2.2 产品目标

1. 客服进入系统后，10 秒内知道最需要处理的工单。
2. 打开工单后，30 秒内看懂问题、关键事实和推荐动作。
3. 简单工单在 2 分钟内完成处理。
4. 未审批的退款、赔付和确定性承诺不能发送。
5. 每条建议都能看到业务依据，但默认不展示技术执行过程。

### 2.3 明确不做

- 不把模型、Agent、Token、Trace、缓存、P95 当作客服卖点。
- 不在客服端展示研发评测和灰度实验。
- 不为体现“智能”而增加新的 Agent 名称或动画。
- 不把模拟订单、模拟物流或 stub 结果宣传为生产能力。
- 不替代现有订单、支付、物流或客服主系统。

## 3. 信息架构改造

### 3.1 客服端

仅保留四个一级入口：

1. **我的待办**：今天必须处理的工单。
2. **全部工单**：搜索、筛选、查看历史工单。
3. **政策查询**：按问题和平台查询当前生效规则。
4. **已完成**：查看本人已处理工单和退回原因。

首页只展示行动型数据：

- 即将超时；
- 等待我回复；
- 等待客户补充；
- 待主管审批；
- 今日已完成。

### 3.2 主管端

仅保留：

- 待我审批；
- 升级工单；
- 团队待办；
- 处理质量。

审批页重点展示：动作、金额、订单事实、政策依据、风险原因、客服拟回复和审批记录。

### 3.3 管理端

单独放置：

- 业务接口；
- 政策版本；
- 用户与权限；
- 审计记录；
- 系统运行；
- 模型与评测。

技术数据可以保留，但不得出现在客服和主管的日常工作首页。

## 4. 功能取舍

| 当前能力 | 决策 | 改造方式 | 实用价值 |
|---|---|---|---|
| 工单列表 | 保留并重做 | 默认显示待办优先级、剩余时限和下一步动作 | 帮客服决定先处理哪一单 |
| 订单/物流事实 | 保留 | 只显示与当前问题有关的关键事实，附查询时间 | 减少跨系统查询 |
| 政策检索 | 保留并加强 | 展示适用结论、关键条款、生效版本和适用范围 | 防止引用错误政策 |
| 处理建议 | 保留并重做 | 使用“建议动作、原因、限制条件、下一步”结构 | 直接支持业务决策 |
| 回复草稿 | 保留并加强 | 根据审批状态限制措辞，支持编辑、预览和发送 | 降低回复时间和承诺风险 |
| 主管审批 | 保留并重做 | 一屏完成核验、修改、批准或驳回 | 减少审批来回沟通 |
| Agent执行步骤 | 移出客服端 | 放入管理后台的技术详情 | 仅供排障 |
| Token、成本、缓存 | 移出客服端 | 放入管理后台 | 仅供成本和系统运维 |
| Trace ID、工作流代码 | 默认隐藏 | 审计或技术详情中按需查看 | 仅供定位故障 |
| 置信度小数 | 删除业务展示 | 转换为“可直接处理／需人工确认／信息不足” | 普通用户能够理解 |
| 灰度实验、Macro-F1、P95 | 移入管理后台 | 使用中文解释和决策建议 | 仅供产品、算法和研发 |
| 通用产品诊断平台 | 从主产品剥离 | 独立路径或独立产品，不出现在售后导航 | 避免定位混乱 |

## 5. 核心页面设计

### 5.1 客服待办首页

首屏从上到下只包括：

1. 五个待办统计；
2. “现在优先处理”队列；
3. 搜索与筛选；
4. 工单列表。

列表新增两个关键字段：

- **剩余时限**：如“18 分钟后超时”；
- **下一步**：如“回复客户”“补充订单号”“等待审批”。

### 5.2 工单详情

使用固定四段结构：

1. **客户遇到什么问题**；
2. **系统已经核实什么**；
3. **建议怎么处理**；
4. **回复客户并完成工单**。

技术详情默认折叠。无关事实不展示；例如退款问题不应展示所有物流节点和完整历史记录。

### 5.3 主管审批

审批页固定回答：

- 准备执行什么动作？
- 涉及多少钱？
- 钱从哪个业务事实得出？
- 依据哪条政策？
- 是否存在冲突或缺失信息？
- 客服准备对客户说什么？

批准时可以修改回复；驳回必须选择或填写原因，原因回传给客服。

### 5.4 政策查询

客服看到的是“我应该怎么处理”，而不是文档库结构。搜索结果首先显示：

- 是否适用；
- 适用条件；
- 允许动作；
- 需要审批的条件；
- 当前生效版本。

政策原文、历史版本和检索细节作为次级信息。

## 6. 关键业务安全规则

以下规则必须由后端强制，不能只依赖界面：

1. 建议动作必须与引用政策的允许动作一致。
2. 退款、赔付等金额必须来自订单/支付事实或确定性规则。
3. 待审批状态下，回复中禁止出现“已退款”“将到账”等确定性承诺。
4. 政策过期、事实过期或接口失败时，不得生成可直接执行的建议。
5. 每个写操作必须校验权限、工单状态和幂等键。
6. 测试数据与生产数据使用不同环境或租户，不能混合展示。

## 7. 分阶段实施计划

> 工期是基于“复用现有后端底座、1 名前端 + 1 名后端 + 1 名测试、产品负责人参与评审”的估算。人员变化后应重新估算。

### 阶段 0：产品基线确认（2–3 个工作日）

任务：

- 确认首个真实业务平台、店铺类型和工单来源；
- 选出 20 个最高频真实工单；
- 明确退款、补发、赔付的审批边界；
- 确认客服当前工作流程和平均处理时间；
- 冻结客服端一级导航和核心字段。

出口条件：形成真实业务清单，未确认项不得用模拟结果替代。

### 阶段 1：界面和角色收敛（5–7 个工作日）

任务：

- 按客服、主管、管理三类角色重做导航；
- 新建“我的待办”首页；
- 工单详情改为四段式结构；
- 隐藏客服端技术字段；
- 统一业务文案、状态、空状态和错误提示；
- 隔离测试与演示数据。

出口条件：5 名非研发人员在不讲解的情况下能找到并完成一张工单。

### 阶段 2：业务一致性与风险门禁（7–10 个工作日）

任务：

- 增加“建议动作—政策条款”一致性校验；
- 增加审批前回复承诺校验；
- 重构退款、退货、物流、少件、破损五类高频决策规则；
- 增加事实过期、数据缺失和政策冲突处理；
- 增加主管审批修改和驳回闭环；
- 补齐相关单元、集成和端到端测试。

出口条件：高风险动作拦截率 100%，已知政策冲突用例全部被阻断。

### 阶段 3：真实系统接入（时间取决于外部接口）

任务：

- 接入真实订单、支付和物流只读接口；
- 接入真实工单或客服消息渠道；
- 对接退款/补发执行接口时先采用人工确认；
- 建立接口超时、重试、幂等和降级策略；
- 完成数据留存、脱敏和权限评审。

出口条件：在沙箱或测试商户完成端到端闭环，不再依赖模拟事实。

### 阶段 4：试点和生产验收（10–15 个工作日）

任务：

- 选 5–10 名客服进行小流量试点；
- 每人完成不少于 20 个典型工单；
- 记录完成时间、修改率、误操作、求助次数和错误建议；
- 修正高频问题后进行第二轮试点；
- 完成回滚、监控、值班和故障处理预案。

出口条件：达到第 8 节指标后才能申请正式上线。

## 8. 正式交付验收指标

| 指标 | 最低门槛 | 说明 |
|---|---:|---|
| 核心工单任务完成率 | ≥ 95% | 客服可在系统中完成既定业务任务 |
| 无指导完成率 | ≥ 90% | 首次使用者无需研发人员讲解 |
| 平均处理时间改善 | ≥ 30% | 与当前人工基线比较 |
| 政策引用正确率 | ≥ 95% | 建议与适用政策一致 |
| 高风险动作拦截率 | 100% | 未审批不可执行 |
| 未审批确定性承诺发送率 | 0 | 禁止提前承诺退款或赔付 |
| 事实字段来源覆盖率 | 100% | 金额、状态等关键事实可追溯 |
| 客服建议采纳率 | 首轮不设虚假目标 | 先实测，再设合理目标 |
| 严重业务错误 | 0 | 错误退款、越权、重复写操作等 |

## 9. 优先级与版本边界

### P0：没有这些不能试点

- 角色分层和导航收敛；
- 四段式工单详情；
- 建议与政策一致性校验；
- 审批前承诺拦截；
- 测试数据隔离；
- 五类高频工单闭环。

### P1：试点期间完成

- 客服工作量和超时提醒；
- 主管审批修改闭环；
- 政策业务化查询；
- 新手提示、空状态和错误恢复；
- 质检抽查页。

### P2：有真实使用数据后决定

- 自动分配优化；
- 更多问题类型；
- 复杂模型灰度；
- 高级成本分析；
- 自动执行低风险动作。

## 10. 需要用户最终确认的业务问题

这些问题会改变产品方向，正式开发阶段开始前必须由业务负责人确定：

1. 首个目标是自营电商客服、平台店铺客服还是品牌电商客服？
2. 系统最终独立使用，还是嵌入现有客服系统？
3. 首批必须处理的五类工单是否为退款、退货、物流异常、少件和破损？
4. 哪些退款金额需要主管审批，是否按店铺或用户等级变化？
5. 客服是否可以直接发送回复，还是只能复制到原客服系统？

## 11. 本次原型

配套原型：`docs/product-redesign/售后工单系统-实用型原型.html`

原型用于验证信息架构和操作顺序，不调用真实业务接口。原型中的订单、用户、金额和统计均为明确标注的演示数据，不代表生产表现。

## 12. GitHub 对标研究补充

配套研究：`docs/product-redesign/GitHub高星客服项目对标研究.md`

对标研究没有改变“以一线客服为中心”的方向，但补充了以下实施要求：

1. 借鉴 Chatwoot 的统一收件箱、内部备注、快捷回复和订单上下文。
2. 借鉴 Frappe Helpdesk 的客服/客户入口分离、SLA 和分配规则。
3. 借鉴 AgentDesk 的回答可用性门禁：可草拟、信息不足、需人工决定。
4. 借鉴 ChatterMate 的 AI/等待人工/具体坐席处理状态和交接摘要。
5. 借鉴 TGO 的订单、物流、商品和政策结构化卡片，但不把 Agent 编排界面暴露给客服。
6. 多渠道统一工单作为 P1/P2，不抢占退款、退货、物流异常等核心闭环的 P0 资源。
