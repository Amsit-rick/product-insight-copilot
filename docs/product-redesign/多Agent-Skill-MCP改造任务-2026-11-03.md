# 多 Agent、业务 Skill 与 MCP 改造任务

日期：2026-11-03  
状态：实施中（截至 2026-11-04）
规模：Large（跨后端状态、公开接口、前端展示、外部 MCP 与权限安全）

## 一、改造目标

本轮不以“增加技术名词”为目标，而解决三个具体问题：

1. 客服打开工单后，可以直接看懂为什么启动多 Agent、哪些业务角色参与、各自完成了什么、当前卡在哪里。
2. 不同售后场景加载不同的业务核验方法，避免七个 Agent 只有名称不同、实际处理方式雷同。
3. 为订单、支付、物流和售后记录预留标准化的只读 MCP 数据源，同时保留现有权限、预算、审计和规则安全边界。

## 二、明确不做

- 不把所有内部工具重写为 MCP。
- 不允许 Agent 绕过 ToolRegistry 直接连接外部服务。
- 不把金额、风险等级、审批要求和写操作权限交给 Skill 或模型判断。
- 首期不开放退款、补发、赔付、发券等 MCP 写工具。
- 不向普通客服展示 Token、模型名、Prompt、Trace ID 或内部错误堆栈。
- 没有真实 MCP 服务契约时，不宣称 MCP 已经接通生产平台。

## 三、目标架构

```text
工单正文
   ↓
确定性问题分类与风险预判
   ↓
BusinessSkillRegistry 选择场景 Skill
   ↓
AnalysisTask.filters.business_skills
   ↓
售后 LangGraph 条件路由
   ↓
各 Agent 获取与职责相关的 Skill 核验清单
   ↓
ToolRegistry（白名单、知识库权限、预算、审计）
   ↓
MockFactAdapter / HttpFactAdapter / 可选 McpFactAdapter
   ↓
规则引擎决定动作、金额、风险与审批
   ↓
前端展示业务协作路径；技术详情继续按权限折叠
```

## 四、实施任务

### Slice 1：业务化展示多 Agent 协作路径

目标：先解决“用户感受不到多 Agent”。

后端：

- 为工单详情的 `analysis` 增加强类型字段：
  - `mode`: `fast_path | multi_agent`
  - `mode_label`: `快速核验 | 多 Agent 协作`
  - `route_reason`: 为什么采用该模式
  - `agent_count`: 本次实际参与的 Agent 数量
  - `business_steps`: 脱敏后的业务步骤
  - `applied_skills`: 本次加载的业务 Skill
- 每个业务步骤返回：角色名称、参与原因、负责事项、阶段、并行组、状态、业务结论。
- 现有技术步骤 `steps` 保留，模型、Token、延迟和错误仅供管理员/工程角色查看。
- 旧任务缺少 `multi_agent` 时，根据实际 Agent 轨迹兼容推断模式。

前端：

- 在“建议怎么处理”区域增加默认可见的“本次协作处理过程”。
- 完整流程显示“多 Agent 协作 · 7 个业务角色”；快速流程显示“快速核验 · 4 个业务角色”。
- 用业务阶段表达并行：
  - 订单核验 ∥ 政策核验
  - 回复准备 ∥ 风险复核
- 普通客服只看业务结论和当前进度；管理员/工程人员仍可展开原技术详情。
- SSE 进度使用中文业务动作，不向客服暴露 `triage_agent` 等节点代码。

验收：

- 优惠解释工单显示 4 个业务步骤。
- 退款工单显示 7 个业务步骤和主管审批原因。
- 客服无需技术权限即可回答“谁参与、为什么参与、各自完成了什么”。

### Slice 2：售后业务 Skill 注册和选择

新增内部业务 Skill 注册表，首批 Skill：

| Skill | 适用场景 | 核心价值 |
|---|---|---|
| `promotion_explanation` | 优惠未生效 | 核对活动门槛、订单条件和适用政策 |
| `refund_review` | 退款 | 核对实付金额、退款条件、历史退款和审批要求 |
| `logistics_exception` | 物流停滞 | 核对轨迹时间、停滞阈值、补偿政策和跟进周期 |
| `fulfillment_exception` | 少件、漏发、错发 | 核对数量、包裹事实和补发条件 |
| `damage_evidence` | 商品破损 | 核对破损照片、签收状态和补发/退换条件 |
| `quality_guard` | 完整多 Agent 流程 | 检查证据、金额来源、政策版本和回复承诺 |

规则：

- Skill 只包含场景目的、必需证据、各 Agent 核验清单和版本。
- Skill 由确定性分类选择，不允许模型自由加载任意 Skill。
- Skill 元数据写入 `AnalysisTask.filters["business_skills"]`。
- 分类 Agent 完成后，根据最终问题类型重新核准一次 Skill。
- 每个 Agent 只收到与自己职责相关的 Skill 指引，避免提示词重复。
- `AgentRun.output` 记录实际使用的 Skill code/version，便于审计和界面展示。
- Skill 不能覆盖规则引擎生成的动作、金额、风险等级和审批要求。

验收：

- 优惠问题加载 `promotion_explanation`。
- 退款加载 `refund_review + quality_guard`。
- 物流停滞加载 `logistics_exception + quality_guard`。
- 少件、破损分别加载对应 Skill。
- 未知问题仅加载安全质检能力，不猜测业务政策。

### Slice 3：可选只读 MCP 事实适配器

目标：让订单、支付、物流、售后事实可以来自标准化 MCP 服务，但默认仍使用当前 mock/HTTP 适配器。

建议只允许静态映射的只读工具：

- `commerce.get_order`
- `commerce.get_payment`
- `commerce.get_logistics`
- `commerce.get_aftersale`

实现要求：

- 新增 `McpFactAdapter`，实现现有 `FactAdapter` 协议，不修改订单 Agent 调用方式。
- MCP 工具名称由服务端配置静态映射，不接受服务动态返回任意工具。
- MCP URL、鉴权信息、租户和用户身份只能来自服务端配置及 ToolContext。
- MCP 返回值统一转换为现有 `AdapterResult`，包含来源、观测时间、请求 ID、适配器名称和结构化错误。
- 限制超时、重试次数和响应体大小。
- MCP 返回文本一律视为不可信数据，不得作为系统指令或动态 Prompt。
- 健康接口只返回配置状态和能力状态，不回显 URL、Token 或鉴权头。
- SDK 固定版本，升级必须跑契约测试。

首期仅实现禁用默认值、适配器接口、配置校验、健康状态和 mock 契约测试。真正接通外部 MCP 服务前，必须补充：

- 服务地址与传输方式；
- 认证方案；
- 四个工具的输入输出 Schema；
- 租户隔离规则；
- 超时、限流和错误码约定。

### Slice 4：端到端验收

必须覆盖：

1. 优惠未生效：4 Agent + `promotion_explanation`，生成回复草稿。
2. 退款：7 Agent + `refund_review/quality_guard`，金额引用支付事实，L3 等待主管。
3. 物流停滞：7 Agent + `logistics_exception/quality_guard`，生成跟进计划。
4. 破损：7 Agent + `damage_evidence/quality_guard`，缺照片时明确提示。
5. MCP 超时：不生成伪事实，转补信息或人工处理。
6. MCP 返回诱导文本：不能改变工具权限、动作、金额、风险和审批规则。

验证范围：

- 后端 Skill/MCP 单元测试；
- 售后工作流集成测试；
- 后端全量测试；
- 前端 TypeScript 检查和生产构建；
- 浏览器验证优惠、退款和外部事实不可用三条页面路径；
- `git diff --check` 与敏感信息检查。

## 六、实施门禁

批准后按 TDD 顺序执行：先修改/增加测试表达目标行为，再实现 Slice 1 → Slice 2 → Slice 3 → Slice 4。

MCP 真实连接缺少外部服务契约，因此本轮可以完成本地基础层和模拟契约，但不得将“基础层完成”描述成“真实 MCP 已接通”。
