# 发布报告覆盖率门禁 P3-36（2026-11-11）

## 1. 目标与边界

P3-35 修复了政策检索证据契约，但当时虚拟环境和开发锁都没有覆盖率工具，无法对关键发布报告代码给出可重复的覆盖率证据。

P3-36 为 `backend/scripts/after_sales_release_report.py` 建立独立的 **80% 语句覆盖率门禁**，并把同一命令接入本地 `scripts/ci.ps1` 和 GitHub Actions。该数字只描述发布报告关键路径，不代表整个后端、前端或 Agent 决策质量达到 80%。

## 2. 用户旅程与验收保证

- 作为发布负责人，我希望发布报告的门禁组装、人工审批和 CLI 写盘路径有可量化测试证据。
- 作为维护人员，我希望本地 CI 与远程 CI 使用同一覆盖率命令和阈值，避免只在某一环境生效。
- 作为供应链审计人员，我希望覆盖率工具进入 Linux/Windows 哈希锁，但不进入生产运行时锁。

## 3. RED 证据

新增契约测试后，专项结果为 **2 failed / 43 passed**：

1. 依赖锁验证器没有把 `coverage` 视为必需开发依赖，删除该包仍会错误通过；
2. `scripts/ci.ps1` 和 `.github/workflows/ci.yml` 均没有覆盖率执行与 `--fail-under=80` 门禁。

RED 提交：`3c1a40a test(delivery): require release report coverage gate`。

首次真实测量时，原有 33 条发布报告测试只达到 **79%（535 条语句，115 条未覆盖）**，因此没有降低阈值。补充报告组装、机器门禁后人工审批、审批模板和 CLI 写盘/非就绪退出测试后，覆盖率达到 **80%（535 条语句，107 条未覆盖）**。

## 4. GREEN 实现

- `requirements-dev.in` 增加 `coverage>=7.17,<8`；
- 使用 `pip-tools==7.6.2` 和 Python 3.12 分别生成 Linux/CI 与 Windows 哈希锁，固定为 `coverage==7.17.2`；
- 依赖锁验证器要求 `coverage`、`pytest`、`pytest-asyncio` 只能存在于开发锁，不能进入 runtime 锁；
- 本地 CI 与 GitHub CI 执行：
  - `coverage run --include=scripts/after_sales_release_report.py ...`；
  - `coverage report --include=scripts/after_sales_release_report.py --fail-under=80`；
- 覆盖率数据库写入 `backend/.tmp`，普通 `.coverage*` 也加入忽略规则，避免测试产物进入提交。

GREEN 提交：`935d404 feat(delivery): enforce release report coverage gate`。

## 6. 已知边界

- 80% 是发布报告脚本的语句覆盖率，不是全仓覆盖率，也不是分支覆盖率；
- 当前没有把所有 1457 条测试放在 coverage 下执行，避免将大量脚本和外部演练代码的零覆盖混成一个失真的总数字；
- 覆盖率不能替代真实外部平台、跨主机、真实模型 holdout、真人可用性测试或人工发布批准；
- 该门禁只防止关键报告路径覆盖率回退，不能证明每个断言都具有同等业务价值。

## 7. 量化进度

P3-36 本地工程完成度 **100%**。此前“覆盖率未测”的本地缺口已经关闭，关键发布报告路径从无门禁提升为本地/远程统一的 **80% 失败关闭门禁**。

系统整体仍保持 `production_ready=false`；外部生产阻断项没有被覆盖率数字改变。
