## 2. RED：旧运行实例为什么不能继续充当证据

对既有 `pic-ticket-audit` 执行新探针时退出码为 1：

- API readiness 正常，但两个 Worker 没有健康状态；
- API/Worker 没有 CPU、内存和 PID 上限；
- 根文件系统可写，未移除 Linux capabilities，也未启用 `no-new-privileges`；
- 运行容器镜像与当前 `pic-api:local` 不一致；
- `APP_RELEASE_SHA` 未绑定当前提交。

因此“容器持续运行 22 小时”不能替代当前版本、当前镜像和当前加固配置的验证。

首次新镜像构建还暴露了一个可复现性问题：Dockerfile 的 `# syntax=docker/dockerfile:1` 会额外访问 Docker Hub，当前网络在该请求上超时。项目没有使用远程 frontend 专属语法，已移除该声明；固定 digest 的 Node/Python 基础镜像随后可直接从本地缓存解析。

## 3. GREEN：完成的工程改造

### 3.1 生产运行时失败关闭

`APP_ENV=prod` 新增以下启动阻断项：

- `DEBUG=true`；
- SQLite 或非 PostgreSQL 数据库；
- 示例数据库口令；
- 非 Redis 缓存后端；
- 空、通配符、HTTP、本机地址、带凭据或片段的 CORS 来源；
- 默认或示例对象存储凭据。

原有 JWT、自动播种、独立 Worker、Postgres checkpointer、HTTPS 对象存储和可信代理门禁继续保留。非生产环境不受这些新增限制。

### 3.2 容器与镜像

- Node、Python、PostgreSQL/pgvector、Redis、Qdrant 和 MinIO 默认镜像按 SHA-256 digest 固定；
- API、Worker、迁移、调度器和 Sandbox 以非 root 用户运行；
- 应用容器启用只读根文件系统、`cap_drop=ALL`、`no-new-privileges` 和独立 `/tmp` tmpfs；
- API、Worker、迁移、PostgreSQL、Redis、MinIO、Qdrant 等均配置 CPU、内存和 PID 上限；
- Worker 新增不含业务数据的文件心跳，容器健康检查不再仅依赖“PID 仍存在”。

### 3.3 脱敏单机部署探针

新增 `backend/scripts/verify_compose_deployment.py`，检查：

- Compose 服务数量、运行状态和 API/Worker 健康状态；
- readiness 中数据库、Redis、队列、共享 checkpointer 和共享对象存储；
- 非 root、只读根文件系统、能力移除、禁止提权和资源上限；
- 运行镜像是否与期望镜像一致；
- API/Worker 是否绑定期望 Git SHA。

证据不保存原始 URL、密码、Token、环境变量全集、容器 ID、Worker ID 或业务请求正文。
