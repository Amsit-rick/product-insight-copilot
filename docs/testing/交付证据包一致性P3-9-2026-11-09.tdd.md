# 交付证据包一致性 P3-9 TDD 记录

日期：2026-11-09

## 问题

P3-8 已能只读展示预发布报告和交付检查，但仍有两个交付缺口：

1. 两个 JSON 分别更新时，应用可能读到跨批次组合；
2. 把“绑定当前提交”的证据写回并提交到同一 Git 仓库，会让 HEAD 再次变化，形成证据自引用。

因此正式证据必须作为 CI/交付流程生成的独立只读制品注入，而不是靠仓库内文件自证当前发布版本。

## RED

先新增以下失败用例：

- report/check 存在但 manifest 缺失时必须失败关闭；
- manifest 生成后任一文件发生字节变化时必须失败关闭；
- manifest 发布 SHA 与报告发布 SHA 不一致时必须失败关闭；
- 交付检查的 `source_report_generated_at` 不属于当前报告批次时，打包脚本必须拒绝。

实现前专项结果为 `4 passed / 3 failed`。失败证明旧服务会把缺 manifest、文件被改或版本不一致的目录继续判为 `current`。

## GREEN

### 证据包契约

新增 `delivery-evidence-manifest-v1`：

- `release_sha` 绑定预发布报告中的发布提交；
- `files` 固定包含预发布报告和交付检查；
- 每个文件记录 SHA-256 和自身带时区生成时间；
- `bundle_id` 由发布 SHA 与两个文件清单确定；
- manifest 采用临时文件替换方式原子写入。

应用读取时依次验证 manifest schema、两个文件哈希、文件生成时间、同批次关系和发布 SHA；任一步不确定都返回 `trusted_production_ready=false`。

## 部署方式

- 本地 CI 在报告和检查之后调用 `package_delivery_evidence.py`；
- Compose 使用 `DELIVERY_EVIDENCE_HOST_DIR` 指定宿主证据包目录，并只读挂载到容器；
- 仓库目录仅作为本地默认值，生产应使用 CI/交付系统产出的独立制品目录；
- `APP_RELEASE_SHA` 仍由部署环境注入，必须与 manifest 的 `release_sha` 匹配。

## 边界

证据包一致只证明“展示的两份证据没有被替换或跨批次拼接”，不证明外部门禁已经完成。真实事实 sandbox、真实指标源、外部 Webhook、跨主机环境、真实模型 holdout、真人客服测试与授权审批仍然缺失。
