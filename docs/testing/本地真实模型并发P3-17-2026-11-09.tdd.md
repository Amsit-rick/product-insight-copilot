# 本地真实模型并发 P3-17（2026-11-09）

## 结论

本阶段完成了真实本地 Embedding/Reranker HTTP 服务的并发压测器和混合负载验证。

本机 CPU ONNX 结果显示：Embedding 本身较快；8 候选 Reranker 是主要瓶颈，吞吐约 3 QPS，并发从 1 增加到 4 几乎不提升吞吐，P95 从 360.37ms 增加到 1,426.13ms。单进程本地模型服务不具备生产并发证据。

当前 `production_ready=false`，不能把本机结果外推到目标服务器、GPU、多进程或独立模型服务。

## 负优化实验

审计时尝试把 Embedding 和 Reranker 改成两把独立锁，期望消除混合负载的队头阻塞。真实复测结果：

| 并发 4 混合负载 | 共享锁 | 拆分锁 |
|---|---:|---:|
| Embedding P95 | 725.33ms | 11.55ms |
| Reranker P95 | 724.51ms | 1,426.52ms |
| 总 QPS | 6.17 | 5.79 |

拆锁只是把排队从 Embedding 转移到 Reranker，总吞吐没有提升，Reranker 长尾明显恶化。因此该改动已回退，没有把局部指标改善包装成系统优化。

## 判读

1. 单条 Embedding 并发 2 后吞吐已接近平台，继续加并发主要增加延迟。
2. 批量 8 在并发 2 时约 42.6 请求/秒，即约 341 条文本/秒；并发 4 没有继续提升。
3. Reranker 是完整检索链路主要本地模型瓶颈；并发增加时吞吐约 3 QPS 不变，延迟近似按排队深度增长。
4. 共享串行策略在单进程 CPU 环境下保守但可预测；简单拆锁不是正确扩容方案。
5. 真正的下一步应在目标硬件验证独立 Embedding/Reranker 进程、动态批处理或 GPU 推理，再决定进程数和并发门槛。

## 边界

- 直接端点压测不含向量库、数据库、网络跨主机和 Agent 编排；
