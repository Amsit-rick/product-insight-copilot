## 1. 问题与目标

项目已经具备真实上游适配器和发布门禁，但没有一套统一、可独立启动的参考上游。开发者需要分别
理解事实参考 API、指标适配器和 Webhook 本地探针，无法用一个服务验证完整集成路径。

本阶段目标：

1. 提供订单、支付、物流、售后四类只读事实接口；
2. 提供标准化只读指标源，覆盖成功、未知指标、跨租户、429 和 503；
3. 提供 HMAC Webhook 接收端，覆盖成功、签名失败、503 重试、400 死信和重放；
4. 提供真实 HTTP 活体验证器，证据不保存地址、密钥、请求正文、事实值或指标值；
5. 提供默认关闭的 Docker Compose `sandbox` profile，且不依赖 Postgres、Redis 或正式配置。

## 5. 安全与边界

- Sandbox 只包含只读 `GET` 事实/指标接口和用于测试投递的 Webhook 接收端；
- 不提供退款、赔付、改价、补发、消息发送或任意 SQL；
- Webhook 内存状态不保存正文；
- API Key 和 HMAC Secret 通过环境变量注入；
- 验证报告不保存 URL、密钥、请求正文、订单值或指标值；
- Compose 服务只在显式 `sandbox` profile 下启动，没有 `depends_on`，不继承 `pic-env`；
- 旧 `reference_fact_api.py` 保留兼容，新接入优先使用统一服务。
