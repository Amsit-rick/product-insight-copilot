# 数据库迁移快照恢复 P3-32（2026-11-10）

## 1. 目标与边界

P3-30 / P3-31 已能在 current 与 rollback 镜像迁移清单相同时证明“本次无需数据库回退”，但迁移集合真正发生变化时只能失败关闭，尚不能证明数据层能够恢复。

P3-32 补齐真实迁移变化场景：发布前创建 PostgreSQL 快照，在候选迁移和快照后写入发生后，将快照恢复到隔离数据库，并核对迁移历史、业务数据和公共 schema 指纹。正式迁移保持前向不可变，本阶段不生成破坏性 DOWN SQL。

本阶段证据仅适用于本地一次性 PostgreSQL 16 + pgvector 演练。它不替代生产备份平台、备份加密、异地保存、保留策略、权限审计、容量验证和正式 RPO/RTO 演练。

## 3. 工程改造

### 3.1 独立数据库回滚证据验证器

新增 `backend/scripts/verify_database_rollback_evidence.py`，使用 `database-migration-rollback-verification-v1` 契约校验：

- 证据已执行、已通过且在允许时效内；
- current / rollback 完整 Git SHA 精确匹配；
- 迁移数量和有序迁移清单 SHA-256 精确匹配；
- 候选迁移确实改变 schema；
- 快照、迁移、快照后写入、隔离恢复、迁移历史和业务数据检查全部通过；
- `restored_schema_sha256 == baseline_schema_sha256`；
- `candidate_schema_sha256 != baseline_schema_sha256`；
- 输入不得自称 `production_ready=true`。

任一条件不满足时退出非零，rollout 不会启动本地 Registry 或应用环境。

### 3.2 PostgreSQL 快照恢复演练

新增 `scripts/rehearse-database-migration-rollback.ps1`。流程为：

1. 从 current / rollback 镜像提取迁移清单；
2. 启动按 digest 固定的一次性 PostgreSQL 16 + pgvector；
3. 应用 rollback 镜像的 15 个基线迁移；
4. 写入业务恢复探针 `restore_probe=before-migration`；
5. 使用 `pg_dump -Fc` 创建发布前快照；
6. 应用候选镜像新增的第 16 个 fixture 迁移；
7. 写入快照后数据；
8. 使用 `pg_restore --exit-on-error` 恢复到隔离数据库；
9. 核对迁移历史、业务探针、候选结构消失和 schema 指纹；
10. 清理一次性容器和临时目录。

`backend/tests/fixtures/database-rollback/016_p3_32_release_marker.sql` 只用于验收真实迁移变化，不进入正式 `backend/migrations`，不改变生产迁移历史。

### 3.3 rollout 消费恢复证据

`scripts/rehearse-registry-rollback.ps1` 新增 `-DatabaseRollbackEvidence`。当两个镜像迁移清单不同时，必须先通过独立验证器，并精确绑定同一 current / rollback 镜像，才允许继续发布。

最终 rollout 证据为：

```text
database_migration_change_detected=true
database_migration_rollback_required=true
database_migration_rollback_exercised=true
database_release_safety_verified=true
database_release_basis=snapshot_restore_rehearsed
production_ready=false
```
