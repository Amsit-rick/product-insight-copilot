# 跨平台供应链 Runner P3-22（2026-11-10）

## 1. 目标与边界

本轮将 P3-21 的镜像 provenance/SBOM 构建和验证逻辑从 GitHub Actions 内联命令抽成平台无关的 Bash 脚本，使 GitHub Runner 与 Gitee Go 自托管 Docker Runner 可以调用同一实现，减少两套 CI 逻辑漂移。

真实验证在本机 Docker Desktop 上，通过官方 Docker CLI Linux 容器挂载 Docker socket 并启用 host 网络完成。它证明 Linux Runner 形态可以执行完整脚本，但仍与发布端共享同一个 Docker daemon，不属于 Gitee 托管运行、企业 Registry 或跨主机验证。

## 2. 完成的工程改造

### 2.1 平台无关执行脚本

- 新增 `scripts/ci-image-attestations.sh`，使用 Bash 严格模式并绑定当前 Git HEAD；
- 脏工作区、SHA 不一致、Docker daemon/Buildx/Compose 不可用、Compose 项目冲突均失败关闭；
- 自动启动回环 Registry、等待就绪、构建并 push 带 SLSA provenance 和 SPDX SBOM 的镜像；
- 调用统一 Python 验证器生成提交绑定证据；
- 使用退出 trap 自动清理 Registry 容器、网络和卷。

### 2.2 CI 平台接入

- GitHub Actions `supply-chain` 任务改为调用统一脚本，保留 Buildx insecure loopback 配置与提交绑定 artifact；
- 新增 Gitee Go 导入模板，明确要求配置真实 `DOCKER_HOST_GROUP_ID` 和 Docker 类型自托管 Runner；
- 模板默认仅允许手工触发，并在 host group 占位符未替换时失败；
- 没有创建一个带假 host group ID 的活动流水线，也没有声称 Gitee 已经运行。

## 3. 运行中发现并修复的问题

Windows 的 WSL 发行版能找到 Docker Desktop 命令入口，但未启用 Docker 集成。Docker 调用失败时会向输出写入说明文字，首版脚本把这段文字误判为“Compose 项目已存在”。

修复后脚本会先独立检查 Docker daemon、Buildx 和 Compose；Compose 项目查询同时检查退出码与容器结果。当前 WSL 会准确报告 `Docker daemon is unavailable to this runner`，不再输出错误根因。
