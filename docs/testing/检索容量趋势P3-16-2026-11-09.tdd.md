# 检索容量趋势 P3-16（2026-11-09）

## 结论

本阶段完成了隔离、可复核、失败关闭的检索容量压测器，并在本机对 1,000 / 4,000 / 10,000 切片完成实跑。

结果证明：SQLite `FallbackVectorStore` 的 O(n) 扫描不适合作为生产检索后端。10,000 切片时单并发 P95 为 2.06 秒，并发 4 时 P95 为 8.34 秒；并发没有提高吞吐，反而显著放大单请求延迟。

这不是 pgvector/Qdrant 性能结论，也不是语义质量评测。当前仍为 `production_ready=false`。

## 压测器整改

`backend/scripts/benchmark_retrieval.py` 新增：

- 强制隔离使用 512 维 stub 查询向量、内存缓存和 fallback 后端，不继承真实模型或外部向量库；
- 参数合法性与维度一致性校验；
- 固定随机种子，保证合成向量可复现；
- 查询请求数、成功数、错误数、P50/P95/最大延迟、QPS 和总耗时；
- 预计算向量载入吞吐、SQLite 存储占用和缓存冷热路径；
- 默认输出结构化 JSON；
- 任一查询错误即退出 1；显式提供 P95 阈值时，超阈值也退出 1；
- 固定 `quality_claim_allowed=false`、`production_ready=false`；
- 未提供业务阈值时明确写入 `acceptance_evaluated=false`。

## 判读

1. 单并发延迟随切片数近似线性增长，符合 O(n) 全量扫描特征。
2. 并发 4 的吞吐与单并发基本相同，P95 却约放大 4 倍，说明线程只在扫描链路排队。
3. 缓存能显著加速完全重复问题，但不能解决首次查询、长尾问题、缓存失效或多样化问题。
4. 10,000 条预计算向量已占约 124MiB；生产文档、元数据、真实模型和多租户会进一步增加成本。
5. JSON 中 `passed=true` 只表示 72 次查询全部执行成功；由于没有业务方阈值，`acceptance_evaluated=false`，不能解释为性能达标。

## 边界

- 文本和向量是合成数据，不产生 Recall/MRR 结论；
- 查询 Embedding 为 stub，不含真实模型和网络延迟；
- 载入吞吐不含文档解析、切片和 Embedding 生成；
- 本机 SQLite 结果不能外推至 pgvector、Qdrant、Milvus 或目标生产硬件；
- 正式生产证据仍需目标向量库规模压测、真实模型并发压测和独立人工 Holdout。
