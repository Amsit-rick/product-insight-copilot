# 自托管 Runner 准入与证据绑定 P3-25（2026-11-10）

## 1. 目标与边界

P3-24 已确认 Gitee 托管 Python 执行器没有 Docker CLI、daemon、Buildx 和 Compose。本阶段不绕过门禁，而是为具备 Docker 能力的自托管 Runner 建立可执行准入、镜像证明、签名和证据绑定闭环。

本阶段分五项：

1. Runner 主机准入验证器；
2. provenance/SBOM/签名证据统一入口；
3. 三类证据同一提交、同一镜像 digest 绑定；
4. 本地 Linux Runner 形态真实演练；
5. Gitee 企业主机组真实远程执行与 artifact 下载复验。

第 5 项需要企业 Gitee Go 主机组和独立 Runner，当前环境不具备，不能用本机 Docker Desktop 代替。

## 2. 工程改造

### 2.1 Runner 准入验证

新增 `backend/scripts/verify_self_hosted_runner.py`：

- 校验 Git、Bash、curl、Python、Docker CLI、daemon、Buildx 和 Compose；
- 强制提交 SHA 与 Git HEAD 一致、工作区干净；
- 自托管 scope 强制 Linux/amd64、非 root 用户、本地 Docker endpoint、真实主机组 ID；
- 默认门槛为 4 GiB 内存和 10 GiB 可用磁盘；
- 主机组 ID 只保存 SHA-256 前 16 位指纹，不输出原值；
- 无论通过与否都固定 `production_ready=false`。

本地演练 scope 允许 Windows Docker Desktop 或一次性 root 容器，但证据固定为 `local_host_rehearsal`，不设置 `self_hosted_runner_verified=true`。

### 2.2 统一执行与证据绑定

新增 `scripts/ci-self-hosted-supply-chain.sh`：

1. 执行 Runner 准入；
2. 调用已有 `ci-image-attestations.sh`；
3. 构建带 SLSA provenance 和 SPDX SBOM 的镜像；
4. 使用一次性离线 Cosign 密钥签名并验签；
5. 调用 `package_self_hosted_supply_chain_evidence.py` 生成绑定清单。

绑定器要求 Runner、attestation、signature 三份证据拥有相同完整 Git SHA，attestation index digest 必须等于签名镜像 digest。任一证据声明生产就绪、scope 不一致、SHA 不一致或 digest 不一致均失败关闭。

### 2.3 Gitee 模板

`docs/integrations/gitee-go-supply-chain.example.yml` 已升级为企业主机组模板：

- 显式使用 `hostGroupType: docker`；
- 通过 `${GITEE_COMMIT}` 绑定提交；
- 调用统一自托管入口；
- 上传 Runner 准入、attestation、signature 和 bundle 四份 artifact；
- 仍保留占位主机组 ID，不注册为活动流水线，避免个人仓库伪造企业执行条件。

## 6. 企业主机组接入条件

真实自托管 Runner 必须同时满足：

- 企业 Gitee Go 可创建 Docker 主机组；
- Linux/amd64、非 root Agent 用户；
- Agent 用户可访问本机 Docker socket，但不通过远程 TCP daemon；
- Git、Bash、curl、Python 3、Docker、Buildx、Compose 已安装；
- 至少 4 GiB 内存、10 GiB 可用磁盘；
- 手工触发模板并下载四份 artifact；
- 本地复验 artifact 哈希、提交 SHA、镜像 digest 和 scope。

当前个人社区仓库没有企业主机组管理能力，因此没有注册假 ID，也没有声称远程自托管执行已经完成。
