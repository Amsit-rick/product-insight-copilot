# 数据库发布安全与统一准入 P3-30 / P3-31（2026-11-10）

## 1. 目标与边界

P3-29 已证明同一代码候选的本地供应链、Registry、应用镜像回滚和目标节点探针能够闭环，但仍有两个交付缺口：

1. rollout 只记录“数据库迁移回滚未执行”，没有判断当前与回滚镜像的迁移集合是否发生变化；
2. 最终发布报告没有强制消费统一候选准入证据，存在后续消费者绕过七类证据一致性门禁的风险。

本阶段只建立数据库迁移感知门禁和统一准入消费链路，不实现虚假的数据库回滚。当前与上一候选迁移清单相同，因此可以证明“本次无需数据库迁移回滚”，不能证明“数据库迁移回滚已经演练”。

## 3. 工程改造

### 3.1 数据库迁移感知 rollout

`scripts/rehearse-registry-rollback.ps1` 现在会在发布前读取 current / previous 镜像的 `/app/migrations/*.sql`，按文件名排序并计算清单 SHA-256。

证据新增：

- `database_migration_change_detected`；
- `database_migration_rollback_required`；
- `database_migration_rollback_exercised`；
- `database_release_safety_verified`；
- `database_release_basis`；
- current / previous 迁移数量、清单哈希和一致性。

规则为失败关闭：清单不同则拒绝继续 rollout，直到补充真实数据库快照恢复或迁移回滚演练。清单相同时记录：

```text
database_migration_change_detected=false
database_migration_rollback_required=false
database_migration_rollback_exercised=false
database_release_safety_verified=true
database_release_basis=migration_inventory_identical
```

### 3.2 统一候选准入成为最终报告硬依赖

- `verify_target_release_admission.py` 的本地 rollout 检查强制要求 `database_release_safety_verified=true`；
- `after_sales_release_report.py` 升级为 `after-sales-release-readiness-v5`；
- 发布证据摘要升级为 `after-sales-release-evidence-v2`；
- 最终机器门禁必须消费新鲜、同提交、哈希完整的 `target-release-admission-v1`；

- 证据打包与运行时交付就绪消费者同步接受 v5 契约。
