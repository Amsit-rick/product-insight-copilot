## 1. 结论摘要

系统已经具备登录、工单列表、工单详情、Agent 分析、回复草稿、审批和权限控制等主要功能外壳，本地自动化测试及前端构建能够通过。

当前不能交付的核心原因不是“页面或接口数量不足”，而是：

1. 事实、规则、模型和质检之间存在业务语义冲突，可能向客服给出错误处理建议。
2. 当前事实数据仍来自 mock 适配器，尚未完成真实 OMS、支付、物流和售后平台验收。
3. 工作区大量改动未进入版本控制，无法从远端仓库复现当前成果。
4. 严格生产预检失败，部署镜像、依赖锁定、回滚、安全配置和 CI 门禁均未达到生产标准。
5. 真人无指导可用性测试尚未执行，现有文件只是空白测试模板。

此前出现的“接近 99%”只能理解为开发任务完成进度，不能作为交付成熟度。建议以后固定分开报告：功能开发进度、本地演示完整度、生产成熟度和发布门禁状态。

## 4. P0 阻断缺陷

### P0-01 已签收订单仍被建议补发

**复现工单**：`EVAL-tk-eval-004` / 订单 `TB202609241742`

**运行时证据**：

- 客户原话：“我买的东西到现在还没有发货。”
- mock 订单事实：订单状态“已签收”、最新物流“已签收”、签收时间 `2026-09-24 09:05`。
- 最终建议动作：“补发商品”。

**代码原因**：

- `backend/app/adapters/mock.py:46-64` 将该订单定义为已签收。
- `backend/app/agents/after_sales.py:153-158` 对 `not_shipped` 无条件映射为 `reship`，没有先处理“客户描述与订单事实冲突”。

**风险**：可能造成重复发货、资金损失和错误客服承诺。

**修复要求**：

1. 建立单一的“事实优先”决策入口。
2. 客户文本与订单事实冲突时，禁止直接生成执行动作。
3. 冲突工单应转为“核实订单/物流事实”或人工处理，并明确指出冲突字段。

**验收标准**：

- 已签收事实 + “尚未发货”文本不得产生 `reship`、`refund` 等直接动作。
- 新增参数化测试覆盖未发货、运输中、已签收和签收异常四类事实组合。
- 测试必须断言动作、风险等级、缺失字段和客服草稿四项语义一致。

### P0-02 已存在的事实被错误列为缺失信息

**运行时证据**：页面已经显示支付金额 `156.00`、最新物流“已签收”和签收时间，但 Agent 同时提示缺少实付金额、物流状态和最后轨迹时间。

**代码原因**：

`backend/app/graph/nodes/after_sales.py:269-271` 使用：

```python
decision.get("missing_information") or resolution.get("missing_information") or []
```

规则正确返回空列表 `[]` 时会被视为假值，随后错误采用模型生成的缺失信息。

**修复要求**：必须区分“字段不存在”和“字段存在但为空列表”，规则层明确给出的空列表不得被模型结果覆盖。

**验收标准**：

- `paid_amount`、`latest_track`、`signed_at` 已存在时，缺失信息中不得再次出现对应语义。
- 增加单元测试验证 `[]`、`None`、字段缺失和非空列表四种情况。
- 最终落库前执行一次确定性事实一致性校验。

### P0-03 政策引用与“证据覆盖为 0”同时出现

**运行时证据**：结果页面展示“售后政策-物流时效与补偿标准 v3.0”，质检警告却称“证据覆盖为 0、未命中任何政策条款”。

**代码原因**：`backend/app/graph/nodes/after_sales.py:313-336` 分别保存通用 `evidence_ids` 和 `policy_refs`，但落库前没有验证两者及质检结论是否一致；模型 warnings 会直接进入最终建议。

**修复要求**：

1. 明确定义“政策命中率”和“事实证据覆盖率”，界面不得混用同一个“证据覆盖”文案。
2. 对模型生成的 warnings 做确定性复核，矛盾警告不得落库。
3. 政策引用必须包含政策 ID、版本、条款、适用时间和匹配理由。

**验收标准**：存在有效 `policy_refs` 时不得显示“未命中任何政策”；若政策不适用，应移除引用并说明原因。

### P0-04 当前工作区无法作为版本交付

**现场状态**：

- `main` 与 `origin/main` 均为 `9e966dc`。
- 69 个已跟踪文件被修改。
- 38 个未跟踪项。
- 已跟踪文件约新增 10050 行、删除 1001 行。

**风险**：远端仓库无法复现本机版本，无法进行正式 CI、代码审查、部署和回滚。

**验收标准**：

- 将本轮改造拆分为可审查提交或 PR。
- 从全新目录克隆后，按文档可完成安装、迁移、测试、构建和启动。
- 发布版本必须有不可变 commit SHA 和版本标签。

### P0-05 严格生产预检失败

以下 6 项为当前实际 FAIL：

1. 订单、支付、物流、售后仍为 mock 适配器。
2. JWT_SECRET 仍是示例占位值。
3. CORS 仍为本地开发地址。
4. 生产登录限流没有 Redis 保证。
5. `AUTO_SEED=true`，启动会写入演示数据和演示账号。
6. 本地任务执行后端为 threadpool。

**验收标准**：使用准生产环境变量运行以下命令必须退出码为 0，且不得通过降低检查标准绕过：

```cmd
.venv\Scripts\python.exe backend\scripts\preflight_check.py --strict --json
```

### P0-06 当前部署镜像不包含前端

**代码证据**：`backend/Dockerfile:55-56` 只复制 `app/` 和 `migrations/`；Compose 没有独立 frontend/nginx 服务。应用虽然会尝试挂载 `frontend/dist`，但当前容器中不存在该目录。

**验收标准**：从干净环境执行 Compose 部署后，浏览器访问服务地址必须得到完整登录页和静态资源，而不是只有 API。

## 5. P1 高风险缺陷

### P1-01 “启动分析”要求填写无效字段

- `frontend/src/views/TicketWorkbenchView.vue:615-625` 强制填写“处理说明或审批理由”。
- `frontend/src/api/endpoints.ts:358-361` 的分析请求只发送工单 ID。
- `backend/app/api/routes_tickets.py:818-839` 不接收该理由。

**修复方案二选一**：

1. 分析动作不需要理由：移除输入框和必填校验；或
2. 确实需要理由：扩展 API schema，并将原因写入审计日志和时间线。

不得继续保留“用户被迫填写、后端直接丢弃”的状态。

### P1-02 缺订单号时没有明确补录入口

当前用户点击分析后只能得到“缺少必要事实：订单号”，但详情页没有紧邻错误信息的“补录订单号”动作。

**验收标准**：分析前即完成前端校验；缺订单号时提供补录、向客户索取或转人工三个明确下一步，不进入无意义分析弹窗。

### P1-03 候选门禁名称和逻辑容易误导

`backend/scripts/after_sales_delivery_check.py:57-58` 将 `adapter_mode == "mock"` 作为 PASS；门禁没有覆盖 Git 状态、严格 preflight、完整 E2E、前端构建和镜像内容。

历史报告曾同时出现：

```json
{
  "candidate_ready": true,
  "production_ready": false,
  "mock_mode": true
}
```

**修复要求**：将其重命名为 `local_demo_ready`，生产候选门禁必须单独执行并包含全部硬检查。

### P1-04 CI 未覆盖本轮售后核心回归

`.github/workflows/ci.yml:118` 只运行 `frontend/e2e/smoke.mjs`，未运行：

- `frontend/e2e/after-sales.mjs`
- 严格生产预检
- 售后发布报告和候选门禁
- 镜像内前端可访问性检查

### P1-05 前端依赖不可复现

仓库没有 `package-lock.json`、`pnpm-lock.yaml` 或 `yarn.lock`；CI 使用 `npm install`。`npm audit` 实测报 `ENOLOCK`。

**验收标准**：提交唯一 lockfile，CI 改用 `npm ci`，安全审计可运行并记录结果。

### P1-06 Python 测试环境受到其他项目依赖污染

当前 `.venv/Lib/site-packages/_offline_dev_deps.pth` 引用了以下外部环境：

- `AI_Student/projects/.venv`
- `data_query_agent/.venv`
- `product-insight-copilot/backend/.venv`

因此 904 项测试通过不能证明 `requirements.txt` 在干净环境中足够。

**验收标准**：删除跨项目 `.pth` 依赖后，在全新虚拟环境安装并重新运行全量测试。

### P1-07 健康检查可能假绿

`backend/app/api/routes_system.py:53` 固定返回 `"status": "ok"`。Redis、队列、共享 checkpointer 或向量服务故障时，Docker HEALTHCHECK 仍可能判定健康。

**修复要求**：拆分 `/health/live` 与 `/health/ready`；readiness 必须按生产配置验证关键依赖并在不可用时返回非 2xx。

### P1-08 缺少可执行的迁移回滚

迁移工具只有 `apply`、`status` 和 `list`，没有 downgrade。当前回滚依赖停写和数据库快照，但没有恢复演练证据。

### P1-09 认证与响应头安全不足

- JWT 保存在 `localStorage`，XSS 情况下可直接读取。
- 对正确项目 `8000` 的响应头实测未发现 CSP、X-Frame-Options、X-Content-Type-Options、Referrer-Policy。

建议迁移到 Secure、HttpOnly、SameSite Cookie，并补充 CSP 等安全响应头及对应测试。

## 6. 产品可用性问题

1. 用户无法从界面理解“启动分析”输入框应该填写什么。
2. “处理说明”“审批理由”“分析原因”混用同一个输入框，概念不一致。
3. 工单缺关键事实时只报告错误，没有直接给出可执行修复入口。
4. 页面暴露较多技术语言，如 Agent 节点、coverage、Trace ID；应默认收起，仅向研发或管理员展示。
5. 当前工单列表积累大量 E2E 演示记录和超时数据，普通用户难以区分真实待办与测试数据。
6. 尚无真实客服和主管的无指导完成率、耗时、误操作率与主观反馈。

## 7. 为什么自动化测试通过仍会出现严重业务错误

现有测试主要证明：接口可调用、权限可拦截、页面可操作、mock 流程可结束。它们没有充分覆盖跨模块业务不变量，例如：

- 已签收订单不得按未发货直接补发。
- 已存在的事实不得再次列为缺失。
- 有政策引用时不得同时宣称零政策证据。
- 前端必填字段必须真实传到后端并被使用。
- 模型输出不得覆盖确定性规则给出的空结果。

后续测试必须从“代码路径覆盖”升级到“业务语义一致性验证”。不得通过修改 mock 数据或放宽断言掩盖矛盾。

## 8. 建议整改顺序

### 第一批：先阻止错误客服决策

1. 修复空列表回退问题。
2. 增加事实冲突裁决层。
3. 重写 `not_shipped` 动作规则，使其基于订单事实而非只看客户文本。
4. 统一政策引用、证据覆盖和质检警告口径。
5. 修复“启动分析”无效必填字段和缺订单号补录流程。

### 第二批：建立可信测试与门禁

1. 增加业务不变量测试矩阵。
2. 在 CI 中运行售后 E2E 和严格候选门禁。
3. 建立全新 Python 环境，移除跨项目依赖。
4. 提交前端 lockfile，改用 `npm ci`。
5. 修复候选门禁命名与判定逻辑。

### 第三批：完成可部署交付

1. 将前端加入正式镜像或增加独立前端服务。
2. 提交全部代码并从干净克隆执行交付演练。
3. 补齐 readiness、迁移回滚和安全响应头。
4. 在准生产环境完成 Postgres、Redis、worker 和共享 checkpointer 验证。

### 第四批：完成真实业务验收

1. 接入真实平台 sandbox，禁止使用 mock 通过生产门禁。
2. 使用真实模型和至少 200 条人工标注 holdout 评测。
3. 组织至少 3 名客服和 2 名主管完成 18 项无指导任务。
4. 修复全部 P0/P1 后重新回归，并记录实际完成率和误操作率。

## 9. 开发人员提交修复时必须附带的证据

每个缺陷修复 PR 至少应包含：

1. 缺陷对应的失败测试，证明修复前能够稳定复现。
2. 修复后的单元测试、接口测试或 E2E 结果。
3. 关键业务输入、订单事实、最终动作、风险等级和缺失字段快照。
4. 若涉及模型输出，提供确定性规则的最终裁决结果，不能只提供一段模型文字。
5. 不得使用 mock 结果证明真实平台已接通。
6. 不得以 `candidate_ready=true` 代替 `production_ready=true`。
